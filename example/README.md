# Rivium Storage Android example

A Jetpack Compose (Material 3) app that runs every feature of the Rivium Storage Android SDK. Each feature has its own card with a short note on when to use it, a button, and the real result: the value that came back, or the exact exception the SDK threw. A **Run all checks** screen runs the core flow in one tap, shows pass or fail for each step, and deletes the files it created.

The app is built against the SDK **source** in this repository (`../rivium-storage`, included in `settings.gradle.kts`), not the published `co.rivium:rivium-storage` artifact. So SDK changes you have not released yet can be tested on a phone, in debug and release builds.

## What it shows

| Screen | SDK features |
| --- | --- |
| Setup and sign-in | `RiviumStorage.builder(apiKey)`, `.timeout()`, `.client()`, `.userTokenProvider {}`, `refreshUserToken()` (sign in / out), `setUserToken()`, `setUserTokenProvider()`, `userTokens.value`, `isAwaitingUserToken` / `onAwaitingUserToken` (a "Waiting for a user token — sign in" banner, and a card where a `listFiles` waits for sign-in), `SDK_NAME` / `SDK_VERSION` |
| Run all checks | The core flow against both test buckets (including "calls wait until sign-in": sign out, start a `listFiles`, see it wait, sign in, it completes; and upload progress reaching 100%), with pass / fail per step, then cleanup |
| Buckets | `listBuckets()`, `getBucketByName()`, `getBucket()` |
| Upload | `upload()` with `UploadOptions(contentType, metadata)`: generated bytes, the photo picker, the camera, any file (system picker), the Unicode name `رسید-۸۸۱۲.pdf`, a name with spaces, no content type (guessed from the extension), upload to the same path again (replaces the file), and `onProgress` with a real progress bar on every upload card (plus a generated ~5 MB PNG of noise pixels so the bar visibly moves; a real image/png, so buckets that allow only images accept it) |
| Files | `listFiles()` with `prefix`, `limit` and `cursor` (next page), `getFile()`, `getFileByPath()`, `download()`, `delete()`, `deleteByPath()`, `deleteMany()` |
| Links and images | Public link (public bucket), the 403 for a private file, `download()` + show, a signed link from your server (60 s / 10 min, loaded with no headers), the wrong way (`getUrl(id)` in an image widget) and why, `getDownloadUrl()` with and without headers |
| Image transforms | `getTransformUrl()` with every `ImageTransforms` option: width, height, fit, format, quality, blur, sharpen, rotate. Includes presets, and the result fetched with headers and shown |
| Errors | Not found (`HttpException` 404, `DownloadException`), type not allowed, content that doesn't match its declared type (HTML sent as `image/png`), too big, access denied by rules (403), `executable_blocked` (`.bat` and a fake `.exe`), `token_required` (a call with no user token and `userTokenWaitTimeout(3 s)`; without the limit it would wait for sign-in), `token_invalid`, `token_expired` (a real 60-second token), no network (`NetworkException`) |
| Request log | Every request the SDK sent: path, status, the `X-Rivium-SDK` header, and whether a token was sent. The token itself is never shown. This works through `.client(OkHttpClient)` |

## 1. Test buckets (once per project)

The example uses two buckets:

| Bucket | Settings |
| --- | --- |
| `rivium-example-public` | Visibility **public**. Any file type. No rules (or "Public read"). |
| `rivium-example-private-images` | Visibility **private**. Allowed types `image/*`. Max file size **1 MB**. **Block executable files** on. Rules: template **Users' own folders** (signed-in users read and list everything, but write and delete only under `users/<their id>/`). |

There are two ways to create them:

- **Node.js example server** (easiest): in `../../nodejs/Example`, fill in `.env` and run `npm run setup-buckets`, or call `POST /setup-test-buckets`. It creates both buckets and the rules, and warns about any setting that differs.
- **Console**: open Storage › Buckets › New bucket and use the settings above. Then go to the private bucket's Security tab and apply **Users' own folders**.

## 2. Token server

The app never holds the server secret (`rv_srv_…`). It asks a server for:

- `POST /token` `{"userId": "...", "expiresIn": 3600}` → `{"token": "...", "expiresAt": "..."}`: the Rivium user token for the signed-in user (the token provider).
- `POST /signed-url` `{"fileId": "...", "expiresIn": 600}` → `{"url": "..."}`: a time-limited link to a private file.

With Rivium Auth instead of a token server, the app needs no server for the token: `.userTokenProvider(RiviumAuth.shared.blockingTokenProvider)`, and `storage.refreshUserToken()` from `auth.addAuthStateListener { }`. This example keeps the token server so it runs without Auth set up.

The Node.js example server (`../../nodejs/Example`, `npm run server`) answers both, on port 4000. By default it listens on `127.0.0.1`:

- Android **emulator**: use `http://10.0.2.2:4000` (that is your computer).
- Real **phone** over USB (recommended): run `adb reverse tcp:4000 tcp:4000`, then use `http://localhost:4000`.
- Real **phone** on your Wi-Fi: set `HOST=0.0.0.0` in the server's `.env`, use your computer's LAN address, e.g. `http://192.168.1.20:4000`, and add that IP as one more `<domain>` line in `app/src/main/res/xml/network_security_config.xml`.

The demo server gives a token for any user id. That is fine for testing, but a real server gives one only to the user its own sign-in established. The app allows plain HTTP only to `localhost`, `127.0.0.1` and `10.0.2.2`, so it can reach this local server (`res/xml/network_security_config.xml`); every other host must be HTTPS. Rivium Storage itself is always HTTPS.

Without a token server the app still runs. Requests then carry no user token, so the rule demos show what an unknown user gets, and the signed-link cards say a server is needed.

## 3. Keys

```bash
cp rivium.properties.example rivium.properties
```

Then fill in `rivium.properties`, which git ignores:

```properties
RIVIUM_API_KEY=rv_live_...          # Console > your project > API keys (the PUBLIC key)
TOKEN_SERVER_URL=http://10.0.2.2:4000
PUBLIC_BUCKET=rivium-example-public
PRIVATE_BUCKET=rivium-example-private-images
DEMO_USER_ID=demo-user
```

The values go into `BuildConfig` at build time, so rebuild after changing them. Environment variables with the same names also work, for CI. Never put the server secret here.

## 4. Build and run

Run these from this folder (`sdk/android/example`). It has its own Gradle root, which includes the SDK module from `../rivium-storage`:

```bash
./gradlew :app:assembleDebug        # app/build/outputs/apk/debug/app-debug.apk
./gradlew :app:assembleRelease      # app/build/outputs/apk/release/app-release.apk (R8 on)
./gradlew :app:installDebug         # or installRelease, to a connected phone or emulator
```

- The **release** build turns on R8 (`isMinifyEnabled = true`) and adds **no** keep rules for the SDK (`app/proguard-rules.pro` is empty on purpose). So a release build that works proves the SDK's own `consumer-rules.pro` are enough. It is signed with the debug key so it installs on a test phone; use your own key for a store build.
- `settings.gradle.kts` passes `VERSION_NAME` from `../gradle.properties` to the SDK module, so `X-Rivium-SDK` reports the SDK version being built (for example `android/0.2.1`).
- You can also open this folder in Android Studio and run the `app` configuration.

To check an SDK build on a phone, install debug or release, open **Run all checks** and tap the button. Every step should pass, or be skipped with a reason (for example, no token server). The **file types** step uploads small `.json`, `.csv` and `.md` files to the public bucket with no content type and checks the stored type (`application/json`, `text/csv`, `text/markdown`); it is skipped with a hint if the bucket doesn't allow them. Error steps check the error's `code` (`type_not_allowed`, `file_too_large`, `executable_blocked`), not its message.

**Bucket setup** runs first: it reads both test buckets with the SDK and compares them with what the checks expect (public bucket: public, allows PNG, PDF, TXT, JSON, CSV and Markdown, where no allowed types means any; private bucket: private, images only, max 1 MB; both: Block executable files on), which is exactly what `npm run setup-buckets` in `sdk/nodejs/Example` creates. When they match it passes; otherwise it shows **WARN** with each difference and the Console setting to change (`Console › Storage › Buckets › <name> › Settings › …`), and every check that needs that setting (type not allowed, HTML declared as image/png, `executable_blocked`, upload progress, file types, the PDF / text uploads) is skipped with the same hint instead of failing. A field an older Storage API doesn't send (`blockExecutables`) counts as unknown, not wrong. Against an older Storage API that refuses without an error `code`, the error checks accept the 400 with the known message and add "server sent no code (older Storage API)".

## Notes

- **Showing images.** `getUrl()`, `getDownloadUrl()` and `getTransformUrl()` return API addresses that need the `x-api-key` header (and `x-user-token`). An image loader sends no headers, so don't hand it those addresses. Instead:
  - Public bucket: GET the public-link endpoint once with the key, then use the `url` it returns anywhere.
  - Private bucket: `download()` the bytes, or ask your server for a signed link.
  - Transforms: add the headers to the request (Coil `addHeader`), or fetch the bytes yourself.

  The Links and Transforms screens show each of these.
- The Errors screen expects the bucket settings above. If a bucket is set up differently, the card turns yellow and says what it expected.
